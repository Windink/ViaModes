# ViaModes · Via 视频嗅探播放器

一个适用于 **Via 浏览器（Android）** 的油猴脚本（UserScript），实现「网页视频嗅探 + 全屏沉浸播放器」体验。

- 产物：`dist/via-video-player.user.js`（单文件，~780KB，内含 hls.js）
- 无需 npm 依赖，`node build.mjs` 即可从 `src/` 合并构建

## 功能

### 嗅探
- 拦截 XHR / fetch 网络请求 + DOM 扫描 + 页面文本扫描（支持站内相对地址）
- 资源计时补扫：`PerformanceObserver` + `performance.getEntriesByType('resource')`，能看到脚本注入前和页面自行加载的媒体 URL，补足油猴没有 `chrome.webRequest` 的盲区
- 识别 `mp4 / m3u8 / webm / mkv / flv / mov / avi / mp3 等音视频` 与 blob 原生流
- m3u8 自动识别主清单，合并各码率/音轨/字幕子清单；主清单 body 因 CORS/代理读不到时，也会用 `master/manifest/playlist.m3u8` 的目录登记过滤子目录变体（如 Apple `v2/prog_index.m3u8`）；同时过滤 HLS 的 fMP4 分片（`main.mp4 / init.mp4 / seg-1.mp4`），列表只留可播放的一条，不刷屏
- 自动去重，悬浮角标显示嗅探数量，可拖动换边
- 列表按「能不能播」排序，而不是按抓到的先后：直链 → 视频主清单 → 音轨清单 → `blob:`。嗅探到达顺序本身就是随机的（同一页面两次加载，第一条可能在视频清单和音轨清单之间跳），按到达顺序排会让用户点开就是黑屏
- 音轨清单单独标注 `m3u8·音轨`：有的站点会同时吐出 `/asp/hls/`（视频）和 `/asp/hlsaudio/`、`/asp/audio/…/mp3/`（音轨），不标出来用户分不清为什么只有声音
- `blob:` 永远排最后：它只是页面自己 MSE 会话的句柄，脱离原上下文单独播放必然是 `readyState=0` 的白屏，不能占第一位
- 点开角标 → 底部列表：▶ 内置播放器播放 / ⭳ 下载 / ⧉ 导出给外部播放器

### 选集（剧集列表）
- 入口：播放器顶栏胶囊最左的「选集」按钮、播放器「更多 → 选集」、嗅探面板头部「选集」；脚本菜单里另有「选集（打开剧集列表）」与「选集 诊断」
- 两类来源分开摆，点下去会发生什么一眼可见：
  - **本页剧集**：扫描 `a[href]`（以及带 `data-href / data-url / data-num` 的元素）里带「第 N 集 / EP N / 纯数字」文本的链接，按 **URL 数字模板**分组，只取成员最多、集号互不重复的那一组。当前页所在模板额外加权，避免把分页导航「1 2 3」或侧栏相关推荐当成选集；外域链接与「预告 / 花絮 / 下载」等文本一律排除
  - **嗅探到的视频**：已抓到的多条媒体直链若呈同模板不同数字，本身就是一套分集，点格子**不跳页、直接换源**（最快）
- 点「本页剧集」会跳到该集页面，并在新页面自动接着播（复用连播的 `autoNextLast` 通道）；不想自动播可在脚本菜单关掉「选集跳页后自动播放」
- 站点用 JS 原地切集、没有可跳转地址时，选集只替你点一下那个元素，1.5 秒后重新嗅探：页面吐出新地址就直接换源，没吐出则提示点「刷新」再扫
- 当前集高亮蓝色；网格最多 200 集，360px 窄屏自动换行不溢出；挑集期间控制栏不会自动收起
- **限制**：剧集文本不是数字（「上」「下」「大结局」）、列表画在 canvas 里、或站点切集后完全不重新发媒体请求时认不出来。列表没出来先点菜单「选集 诊断」——它会报出 `a[href]` 总数、像集数的链接数、URL 模板分组与最终集数

### 抗页面广告遮挡
- 角标、嗅探面板、播放器、toast、续播提示统一使用 CSS 最高层级 `2147483647`，并直接挂在 `<html>` 下
- 显示时优先用 `moveBefore` 原子移到 `<html>` 末尾（旧 WebView 回退 `appendChild`），同层级广告也压不过
- 角标 / 面板 / 播放器每 2.5 秒采样检测，只有实际被广告盖住才重新置顶；拖动角标或滑动面板时暂停检测，避免打断操作
- 播放器重排使用原子移动，实测不会中断 `<video>` 播放、不会重置进度

### 网页铺满（原名「页面全屏」）
- 两个入口：脚本菜单「网页铺满 开/关」，以及**播放器顶栏「沉浸全屏」右侧紧邻的「网页铺满」按钮**（开着时点亮）；两条路径共用同一状态源，任意一边开关另一边都会同步
- 做的事只有一件：**把站点自己的播放器（`<video>` / iframe / canvas）放大到整个 WebView 可视区**，不用先打开嗅探播放器。**不调用 `requestFullscreen()`**
- **边界（实测结论，别再按「保留状态栏」理解）**：Via 的地址栏、底部工具栏是 WebView 之外的系统 UI，本功能一概不碰；栏显示与否 100% 由 Via 自己的「下滑隐藏、上滑显示」决定。所以
  - 栏本来就在 → 开启后仍在，视频从页面里的小窗变成铺满可视区（这是它的全部价值）
  - 栏已被滚动藏起 → 还是藏着，JS 叫不回来（`scrollTo` 没有手势，Via 不认）；本功能也**不锁页面滚动**，你像平时一样上滑，Via 自己就把栏显示回来。曾经写过「上滚几个像素叫回栏 + `overflow:hidden` 锁滚动」，真机 A/B 证明无效且让手势失效，已删
- 播放器打开时，网页层右上角那枚「退出网页铺满」胶囊会自动隐藏（顶栏已经有按钮了，不叠两个出口）；关掉播放器后恢复
- 与播放器顶栏那枚「沉浸全屏」是两套独立模式：后者走 `ROOT.requestFullscreen()`，属于系统全屏，会把浏览器栏一起隐藏。两者互斥，用户或站点进入系统全屏时网页铺满自动让位
- 只用 class + `!important` CSS，不写 `<video>` 的 inline style、不搬动 video 节点：MSE / `blob:` 流脱离原节点就黑屏，退出时摘掉 class 即零残留
- 自动挑「正在播放 / 可见面积最大」的主画面；站点延迟插入视频时，1.5 秒巡检会在它出现后自动铺满，视频被移除时自动收起遮罩
- **主画面不在顶层文档也能认**（这三种以前都是「点了完全没反应」）：
  - `<video>` 在 **open shadow root** 里（自研播放器常见）：外层样式表穿不进 shadow root，所以把同一份规则**注入到 root 内部**再挂 class
  - `<video>` 在 **iframe** 里：把 iframe 本身拉满；同源时再往里注入样式，让内层视频跟着满（否则只是空框变大）；跨域读不到 `contentDocument`，按面积识别（≥15% 视口）
  - 画面被画在 **canvas** 上、`<video>` 只是 0 尺寸解码器：video 和 iframe 都挑不出来时才用 canvas 兜底，避免背景动画 canvas 抢走真视频
- 视频与 iframe 之间按「面积 + 是否在播」比较取大者，防止顶层小广告 video 顶掉 iframe 里的大播放器
- 菜单里的「网页铺满 诊断（点了没反应时用）」会报出页面上 video / shadow video / iframe / canvas 各有几个、最终选中的是哪个、尺寸多少——排查时不用猜
- 祖先链的 `transform / filter / perspective` 会把 `position:fixed` 退化成相对该祖先定位（表现为「铺满后视频还缩在原来那一小块」），只给 computed 值非默认的祖先临时清掉，退出还原
- 右上角常驻「退出网页铺满」胶囊：Via 没有 Esc 键，必须有可见出口；放右上而不是右下，避免和底部工具栏区域抢位置
- 层级：黑底遮罩 `2147483000` < 铺满画面 `2147483001` < 角标 / 嗅探面板 / 退出按钮 `2147483647`，铺满期间脚本 UI 依然可点
- 内置播放器打开时自动挂起网页层、关闭后恢复；「强制关闭播放器」逃生门会一并退出网页铺满，避免黑底遮罩被误认成页面卡死
- 不自动开启、不持久化状态：刷新后仍是关闭，符合「只保留手动全屏按钮」的约定

### 流畅度优化（针对“视频卡”）
- 嗅探不再在每次 DOM 变动时全量扫描整页：MutationObserver 只处理新增节点，150ms 合批、每批最多 120 个节点
- XHR/fetch 文本扫描先做 `.m3u8 / .mp4 / ...` 低成本预检，避免对每个 JSON 响应都跑大正则
- 亮度/音量手势只改画面，停手 500ms 后再写存储；关闭播放器或切后台立即落盘，避免每帧同步写 GM
- 播放进度改为每 10s 保存一次，并用内存缓存进度表，减少 GM 同步读写
- **画质红线**：脚本不主动降画质——不按播放器尺寸封顶、不因掉帧降码率、不从最低档起播、并行播放与解码器重试也不钉档；唯一降档入口是「画质」菜单里用户手动选。ABR 按实测带宽自适应仍保留（那是网络能力，不是画质压制），掉帧改由低特效关闭 UI 毛玻璃解决
- HLS 起播交给 ABR 按 2Mbps 估计自动选档（`startLevel: -1`）；缓冲区 36s / 最大 72s / 50MB，回看缓冲压到 20s，把内存让给前向缓冲
- HLS 分片超时按状态切换：正常播放 10s（慢分片尽快失败，让 ABR 降档重试），seek 时放宽到 45s（慢 CDN 也不中途 abort）。有分片正在加载时 watchdog 不再调用 `startLoad`，避免慢 CDN 被反复中断、越等越慢
- 手动切清晰度走 `nextLevel`，等下一个分片边界平滑切换；不再用 `currentLevel`（那会立刻 flush 缓冲重拉，弱网下切完必卡几秒）
- 起播带宽估计从 500kbps 提到 2Mbps，减少前 30 秒在最低档爬坡、每次升档吃空缓冲
- 诊断面板直接输出「下载 X KB/s / 需要 Y KB/s / 负载 Z%」，并给一句结论：源限速、解码超载、还是策略偏紧
- 打开播放器时自动暂停页面里正在播放的背景 `<video>/<audio>`，关闭后恢复，避免抢带宽、抢解码器

### 跳转稳定性
- 手指在播放器上时暂停置顶检测，避免广告重排触发 `touchcancel`，导致“进度条拖了但不跳”
- 进度条的 `touchend` / `touchcancel` 都会提交跳转；横滑 seek 被系统取消时也会提交预览目标
- 统一 seek 入口按 `seekable` 范围夹紧；服务器不支持 Range 时明确提示，而不是静默失败
- HLS seek 超时先重试目标位置，仍失败则回到最近正常播放的位置，不再直接跳回 0
- 慢分片（首字节 20s+）会继续等待而不是中断重来；实测跳到 367s 在约 21s 后成功，无回退、无卡死

### 多页面同时播放的治理（针对“开几个 m3u8 就全挂”）
- 手机上 Via（Android WebView）的视频解码走 MediaCodec，**同时可用的解码器实例数是硬上限**（典型 4~8 个，且分辨率越高越紧张）；Android WebView 不支持原生 HLS，每个 m3u8 页面还要额外跑一套 JS 解封装，CPU/内存开销翻倍
- 关键事实：**切后台的标签页不会释放解码器**，只有页面被销毁（关闭标签）才会还回去。解码器分配失败后 WebView 渲染进程不会重建，于是表现为“所有视频都看不了，只有重启 Via”
- 脚本用一张**跨页面播放登记表**（GM 存储，2.5s 续登、9s 过期）知道还有谁在播，两种模式可切换：
  - **单实例模式（默认）**：只有最早登记的页面在播，其余自动挂起（`stopLoad` + pause）→ 并发解码器压到 1，防耗尽
  - **多页并行模式（脚本菜单 / 播放器菜单可切换）**：允许多个页面同时播，并按并发数自动压缩每页的资源预算：

| 并发页数 | 每页缓冲 | 每页内存上限 | 清晰度 |
| --- | --- | --- | --- |
| 1 | 36s | 50MB | 自动，不封顶 |
| 2 | 20s | 24MB | 自动，不封顶 |
| ≥3 | 12s | 12MB | 自动，不封顶 |

  并行只压缩缓冲与内存，**不动清晰度**；并发解码器的兜底是默认的单实例模式（同一时间只让一页播），而不是压画质。想省资源由用户在「画质」菜单手动选低档
- 挂起超过 20 秒会**彻底销毁 hls.js 实例**释放 MediaCodec，而不是只暂停占着不放；回到前台自动恢复（必要时重建实例并回到原进度）
- 页面切后台时，页面原生 `<video>/<audio>` 与 MSE 流一并深拆（默认「标签页休眠」；关掉则只暂停），页面关闭时销毁实例
- 解码持续失败时给出明确提示而不是静默卡死，并提供「重建播放实例」（菜单里也有）——实例坏掉就地重建，不用重启浏览器
- 脚本菜单新增「强制关闭播放器」：播放器层或页面被卡住时的逃生门，强制拆掉全屏层并解除 `overflow:hidden` 冻结
- 加固了 `closePlayer`：以前任何一步抛错都会导致后面的解冻与移除播放器层不执行，页面被“冻住”后看起来像整个浏览器坏了

### 标签页休眠（回收后台资源）
- 浏览器（Chrome 等）遇到多标签视频卡死时，会**丢弃后台标签页**来回收内存与解码器；Via 的 WebView 没有这套机制，脚本只能自己做一份**更精确的版本**
- 这里做的是**页面级媒体休眠**，不是整页丢弃：
  - 页面切到后台时，把页面里 `<video>/<audio>` 的 `src` **摘掉、清掉 `<source>` 子元素、再 `load()`**——这一步才真正归还 MediaCodec 占用（只 `pause()` 的话元素仍然占着一个解码器）
  - **MSE（`blob:`）同样拆**：以前"怕装不回去"只暂停，结果是后台每页各占一路解码器，开满十个页签时新页签必然拿不到画
  - 卸载前记录 `src` / `currentTime` / 是否在播放 / 静音状态；直链回前台直接装回并回到原进度
  - **MSE 回前台不装回 blob**：让位时站点的 `MediaSource` 已经 closed，再把同一个 `blob:` 赋给 `<video>`
    只会得到一条「有管线、没数据」的假管线——`pipelines` 计数 +1、`readyState` 一直是 0、画面全黑，
    既没恢复播放，又白占一个解码器槽位，正好和「只留当前页」的目标相反。
    现在的做法是让站点自己重建（前台恢复后 hls.js 会发现 media 被 reset 而重新 attach），
    1.8 秒内没画面就弹常驻提示「本页已让出视频解码器，点「重载」恢复播放」
  - **后台页连 `src` 赋值都不许**：只拦 `play()` 挡不住自动连播/预加载——它们先 `src=…` 再 `play()`，
    管线和解码器在 `play()` 之前就已经建好。实测 8 个 m3u8 页签时，后台页会周期性重建 `MediaSource`，
    `pipelines` 在 0/1 之间来回跳（某页 40 秒里跳了 7 次）。现在在 `HTMLMediaElement/HTMLSourceElement.src`
    的 setter 与 `setAttribute('src')` 上直接吞掉后台页的赋值，拉锯从源头消失（自检面板里记作「拦下装源」）
  - 页面 DOM、表单、脚本状态全部保留，只有媒体管线被回收——比浏览器"丢弃标签页"温和得多
  - DRM（`mediaKeys`）流不动，避免破坏鉴权会话
- 内置播放器一进后台就**彻底销毁 hls.js 实例**归还解码器（不再等 20 秒），回前台自动重建并回到原进度
- 前台判定是三个信号叠加：`visibilityState` → rAF 停摆 → 持续失焦 4 秒；
  失焦这条**必须同时有别的页签宣称在台前**才成立，否则点地址栏/系统弹窗会让页面误拆自己
- 除事件外还有 900ms 巡检：后台页每轮检查"还攥着管线吗"，站点趁后台重建播放器会被当场收走
- 脚本菜单可开关：「后台释放解码器 / 标签页休眠（当前：开/关）」，默认开启；关掉后退回"只暂停不释放"的保守行为

### 交给外部播放器（VLC / mpv / N_m3u8DL）
- 站内能播、把链接复制到 VLC 就失败，本质是**链接离开了页面上下文**：缺 Referer 被防盗链挡、缺 Cookie 鉴权不过、签名已过期
- **「用外部播放器播放」**（浮层里的一等按钮，也是播放器菜单项）：生成 `intent://` 链接唤起系统选择器，把播放交给 **另一个 App 的独立进程**去解码。这是"多路并行不打架"的关键——外部播放器各有自己的 MediaCodec 配额，一个崩了也不牵连 Via 的 WebView
  - HLS 用 `application/vnd.apple.mpegurl`，另配一个 `application/x-mpegURL` 兼容按钮（不同播放器注册的 MIME 不一样）
  - 能不能唤起取决于 Via 是否放行外部应用跳转；没反应就用「导出 .m3u」
- 「⧉ 导出给外部播放器」会生成 `.m3u` 播放列表，把当前页 Referer 和 UA 写进 `#EXTVLCOPT`，外部播放器打开就能过防盗链
- 同时提供 `curl -A <UA> -e <Referer> -o xxx.m3u8 <url>`，在电脑上直接拉流或交给 N_m3u8DL-RE
- 「自检兼容性」用三种请求（裸链 / 加 Referer / 再加 Cookie）探测同一地址，状态码一比就知道缺的是哪一项，并直接给结论
- 探测优先用 `GM_xmlhttpRequest` 走 native 通道，不受页面 CORS 限制，行为最接近外部播放器

### 播放器

### 退出播放器时的解码器释放（真机机制）
Android WebView 上 `pause()` 只是停播，MediaCodec 仍被 media 进程持有。真正让它归还的只有
「元素还在文档里时，把 video 打回无资源状态」这一条路径，所以顺序是：

```
stopLoad → detachMedia → destroy(hls)
  → pause → srcObject=null → 摘 src → 清 <source> → load()   ← 元素必须仍在 DOM 中
  → 80ms 后二次硬释放，再移除播放器层
  → 900ms 巡检：实例池非空且播放器已关闭时再补一次
```

**先 `removeChild` 再 `load()` 是无效的**（脱离文档后 load 基本是空操作），这类写法会让解码器一直被占着，
直到整页销毁才归还——表现就是"退出播放器后卡住，关掉页签过一会才恢复"。

### 直接关掉标签页（这条路径不经过 closePlayer）

用户点标签页的 ✕ 时，`closePlayer()` 完全不会执行。此时页面已经在销毁流程里，
**定时器、微任务、异步回调都不会再跑**，所以任何"稍后再释放"的兜底都等不到。
`vvHardTeardown()` 就是为这条路准备的，全部同步完成：

```
停后台定时器/焦点轮询/加载轮询 → stopLoad+detachMedia+destroy 全部 hls 实例
  → 硬释放 VID → 遍历 DOM 里所有 video/audio 逐个硬释放 → 清池、置 _suspended
```

**真机实测（小米 14 Pro / Android 16 / WebView 143，`c2.qti.avc.decoder`）：**

- **Via 关标签页只派发 `beforeunload`，不派发 `pagehide`**。所以清理必须挂在 `beforeunload` 上，
  否则永远不会触发；`pagehide`（非 bfcache）保留作为标准路径的兜底。
- 同一页面三个时刻的状态对比（m3u8，`scripts/android-close-tab.mjs --mode=hls`）：

| 时刻 | video 有 src | paused | hls 池 | 系统 codec |
|---|---|---|---|---|
| 播放中 | true | false | 1 | 存活 1 |
| 关之前一刻 | true | false | 1 | 存活 1 |
| `beforeunload` 清理后 | **false** | **true** | **0** | **destruct=1，存活 0** |

- 清理时间戳 `VV._lastTeardown` 与 beforeunload 同一毫秒，可用来区分"是我们清的"还是"WebView 自己回收的"。
- mp4 / m3u8 两条路径各 3 轮：configure 与 destruct 数量一致，结束存活 0。

> `beforeunload` 可能被取消（页面活下来），所以这条路径不置永久标记、不清定时器；
> `pagehide`（persisted=false）才置 `_vvTornDown` 并清定时器。`pageshow` 会复位该标记，
> 否则 bfcache 恢复后再次关标签页就静默失效了。

### 真机测试的两个 Via 专有坑

1. **`document.write` 插入的 `<script>` 在 Via 里不执行**，必须 `createElement` + `appendChild`。
2. **Via 按 URL 路径缓存子资源**，`?t=` 时间戳和 `Cache-Control: no-store` 都拦不住，
   改了构建仍跑旧版。唯一可靠做法是每次换路径（服务器把 `/dist/vv-<数字>.js` 映射回产物）。
3. 另外：**Via 会把已安装的同名用户脚本注入每个页面**（iframe 不注入）。如果没在 Via 里停用它，
   页面里测到的 `window.__vv` 是 Via 注入的旧版，结论会完全反过来——接口数量对不上就是它。

### 为什么"实例为 0、分片能下载、就是没有画面"

真机上这个组合最容易被误判成"脚本没释放干净"。实际是三个独立问题叠在一起：

1. **`pause()` 不是释放。** `<video>` 只要还挂着资源，就握着一条完整的解码管线（demuxer +
   decoder + renderer），Android 上 MediaCodec 实例不会因为暂停而退回系统。另外按 HTML 规范，
   `removeAttribute('src')` 本身**不会**触发资源选择算法，必须紧跟 `load()`；
   只摘不 load，浏览器手里的播放器毫无变化。**先摘 DOM 再 load 同样是空操作。**
2. **站点自带的播放器才是占用大户。** 现代视频站几乎都用 MSE（`blob:`）。早期版本对 blob
   "只暂停、不摘 src"（怕装不回去），于是后台开五六个视频页就等于五六个解码器不释放。
   设备侧硬件解码器的并发上限通常只有 **8~16**（高通 `c2.qti.avc.decoder` 在 1080p 下实测
   4~6 路就吃紧），所以新页签的表现正是"清单和分片都下载正常、界面不报错、就是不出画"——
   hls.js 把这种情况报成 `MEDIA_ERROR`（`bufferAppendError`），不是网络错误，
   所以按"网络重连"处理永远修不好。
3. **跨页协调走错了存储。** 原来的"求让"广播写在 GM 存储里。`GM_setValue` 是脚本级持久化，
   Via 各标签页各持一份缓存，别的页签读不到最新值、也没有变更事件，求让基本石沉大海。
   只有 **localStorage** 才是同源共享 + 有 `storage` 事件，能做实时协调。

对应修复（都在 `src/` 里）：

- 统一的 `vvDetachMedia()`：`pause → muted → srcObject=null → 摘 src → 清 <source> → load()`。
  少一步就白拆：只摘 `video` 的 `src` 属性再 `load()`，资源选择算法会重新去选 `<source src>`，
  当场又挂一条管线，解码器一路没还。
- **非当前页不持有任何解码器**（核心约束）。后台页一律连 MSE（`blob:`）一起深拆，不再"只暂停"。
  拆之前记下 `src` + 播放进度，回前台先尝试装回；装不回（MediaSource 已被站点 close）才弹
  「本页已让出视频解码器，点此恢复」。
- 打开内置播放器前，先把**同一页**正在播的 media 真拆掉——同页两路在 1080p 下就够顶满配额。
- 求让监听**常驻**（2 秒轮询 + `storage` 事件），并且**双通道**：
  `localStorage`（同源、实时）+ `GM_setValue`（脚本级、跨站；能不能读到取决于壳，先探后用）。
  用户真实用法是多开十个**不同**视频站，只靠 localStorage 等于十个页互不相干。
- **播放门禁**：进入后台 / 已答应让位的页面，`HTMLMediaElement.prototype.play` 直接
  `reject(NotAllowedError)`。只"事后拆"会和站点的自动连播拉锯：它建、我们拆、它再建，
  中间反复向 media 进程申请解码器，本身就是失败操作。用 `NotAllowedError` 是因为
  各家播放器都把它当"被自动播放策略拦了"来处理，不会白屏报错。
- **巡检兜底**（900ms 一轮）：不看事件，只问"我是不是还攥着管线"。站点趁后台重建播放器，
  下一轮就被收走。
- **前台判定三信号**：`visibilityState` → rAF 停摆 → **持续失焦 4 秒**。
  第三条是给多窗口/分屏用的：两个窗口都 visible、rAF 都在跑，只有焦点能区分。
  失焦信号先探测"是否可用"（有的 WebView 恒为 false），否则页面几秒后会把自己拆掉。
- **碰屏幕即宣告主权**（`touchstart/pointerdown`，8 秒节流）：比失焦判定早 4 秒。
  两边都自称前台时，按"最后一次用户操作时间"决胜。
- hls `MEDIA_ERROR` 走"让位 + 管线重建，画质不变"（`vvCodecRescue`），重试三次（0.9s / 2.5s / 5s）——
  别的页从"发现失焦"到真正归还解码器要几秒，只试一次会在解码器还没空出来时就把页面判死。
- 自检面板新增三行：**独占判定**（前台/后台 + 三个原始信号）、**解码器**（本页管线数 /
  已交还 / 巡检轮次 / 拦下起播次数）、**跨页通道**（走通了 GM 还是只有 localStorage）。
  多页签播不动时看这三行，就能分清是"没判定成后台"、"判定对了但没还"、还是"跨页协调不通"。

### 为什么"画面在动、却没有声音"

把解码器交出去，最省事的做法是 `pause() + muted = true`（`pause` 在部分机型上延迟生效，
不静音会有残余音频漏出来）。问题在于**静音是临时状态**，而"回到前台"的路径远不止一条：
`visibilitychange`、页面冻结后的 `resume`、bfcache 的 `pageshow`、宿主（Via）自己的前后台切换、
还有站点在后台把播放器整个重建一遍。少还原任何一条，用户看到的就是"切回来画面在动、一点声音没有"。

三个具体成因与修复：

- **临时静音没配套还原**。拆解时把用户原本的 `muted` / `volume` 记进 `__vvMuted` / `__vvVol`，
  装回（`vvAttachMedia`）、解冻（`vvThawMedia`）、重建（`vvLoadMedia`）都要原样还回去。
  硬释放会把 `volume` 压成 0，所以**只还原 `muted` 不够**——两个开关，漏一个照样没声。
- **临时静音被当成了"用户的选择"**。休眠/换播放器时会再记一次"当前静音状态"，
  如果那一刻正好是临时静音，记下来的就是"用户要静音"，之后永远静音。
  现在统一走 `vvOrigMuted()`：有 `__vvMuted` 就用它，别读元素此刻的值。
- **音量持久化的坑**。老版本只手势存 `vol`，一次滑到底（`vol=0`）就变成永久静音，
  界面上还没有任何按钮能看出音量为 0。现在 `vol` 只存非零值，静音单独记 `mute`；
  读到历史 `vol=0` 自动当 1。

再加一层**幂等兜底**（`vvRestorePageAudio` / `vvRestorePlayerAudio`，回前台立刻一次 + 900ms 巡检）：
只要这页在前台、没有"挂起待恢复"的记录、用户也没主动静音，任何被我们压过静音的元素一律还原。
不依赖具体是哪条路径把它弄静的——补路径永远补不完。

自检面板因此多了第 4 行：`声音: muted=false vol=1  存储 vol=1 mute=0`，
一眼能分清"是我们的临时静音没还原"还是"站点自己把 video 设成静音"。

> 判据补充：用户反馈**页面自带的播放器也一起播不了**。这是关键分野——
> 如果只有脚本播放器黑，问题在脚本；**连站点播放器都起不来，就是设备级解码器配额被占满**，
> 脚本能做的是"少占、快还、跨页协调"，不可能凭空造出解码器。

### 为什么"有的网站开十几个都没事，有的站开一个就卡死"

这句反馈最初被当成"站点自身的问题"。用 `scripts/perf-heavy.mjs` 把负载固定成同一份
（3×1.2MB 的 `text/javascript`、每秒 12 个 48KB JSON 接口、每秒 120 个新增节点 + 懒加载改 `src`），
只切换"注入脚本 / 不注入"，才把两者分开。结论是：**站点特性会放大我们自己的三个漏洞**，
而且第三条一旦触发就不可自愈——页面看着像死了。

**① 把不需要的响应体整份复制了一遍。**
`fetch` 分支原本只要 `Content-Type` 以 `text` 开头就读 `resp.clone().text()`，
即每个 JS / CSS / HTML 响应都被复制成字符串再跑正则。`clone()` 本身就是一次流复制，
代价在"决定读不读"之前就付掉了。改成先过闸门（只放行 json / plain / 表单 / m3u8 清单，
且 ≤256KB）后，同一份负载 14 秒里省掉 **39 次读取、约 11.7MB** 的字符串复制。
XHR 侧同理：`responseText` 对大响应会强制解码，也在读之前拦。

**② DOM 变更队列没有上限。**
`vvMoQueue` 原本只增不减。瀑布流 / 弹幕 / 自动轮播的站点，节点生产速度长期高于消费速度，
队列会一路涨到几十万，内存翻倍、主线程被自己的扫描任务占满。
现在有三道约束：队列上限 320（超出丢最旧的并计数）、每批只占 8ms（按毫秒切而不是按"120 个"）、
`vvCheckMediaNode` 用 `nodeName` 粗筛（懒加载图片改 `src` 不再送进 URL 解析）。

**③ 一次长任务被误判成"用户切走了"，然后页面被钉死。**
这是"卡死"最真实的形态。前后台判定里有一条 rAF 心跳：`requestAnimationFrame` 断了就判后台。
阈值原本是 1.6 秒——而重页面首屏解析、瀑布流批量渲染、广告 SDK 同步计算，随便就是 1~2 秒。
误判之后我们不仅拆掉解码器，还在 `src` 的 setter 上**拦住它重建**，站点于是永远停在加载圈上。

修复分两层：

- rAF 阈值提到 2.6 秒，并且**必须同时拿到硬证据**（`document.hidden` 或"别的页签宣称在台前"）才认。
  只剩"rAF 断了"这一个信号时，最可能的解释是本页主线程被卡住了，不是切走。
- 把"拦建源"的门禁收紧成 `vvSrcGateActive()`：只在 document 真隐藏、有 peer 证据、
  或用户主动让位时才拦。**拦 `play()` 拦错了站点还有兜底（显示"点击播放"），
  拦 `src` 拦错了就是永久黑屏**，两者不该用同一套证据。

验证方式就写在压测里：每 6 秒把主线程卡 2 秒，共 3 次，跑完看自检——
`被判后台 0 次 · 拦下建源 0 次 · 页面视频有源=true 管线=1`。

**④ 关页签时把同一件同步重活干了两遍。**
`beforeunload` 和 `pagehide` 会先后各调一次 `vvHardTeardown`，两次都对页面上**所有** `video/audio`
做 `removeAttribute('src') + load()`。广告站/信息流页面上常躺着几十个预加载的空 `<video>`，
而这条路径是同步的——用户感知就是"点关闭，浏览器卡住两秒才反应"。
现在：媒体释放一轮只做一次，且只处理"真挂着源"的元素、最多 12 个（系统解码器上限本来只有个位数）；
定时器清理仍由 `pagehide` 那次负责，不会被一起去重掉。

顺带：`vvActiveTouch` 的活跃心跳原本每 2 秒写一次 `localStorage`（同步磁盘操作）。
十几个页签各写各的，累积起来是实打实的主线程阻塞。现在只在状态变化或心跳快过期（6 秒）时写。

自检面板多了一行，用来区分"这站本来就卡"和"被我们拖卡"：

```
嗅探开销: 条目 3  DOM 1562(丢弃120)  省读 39 次/11.7MB
```

`丢弃` 不为 0 说明页面的 DOM 增速超过了我们的处理速度；`省读` 是被闸门挡下的、读了也没用的响应体。

### 播放态掉帧：毛玻璃的每帧重算

重站压测（`perf-heavy.mjs`）覆盖不到这个场景——它根本没打开内置播放器。视频画面在动时，
`.vv-sheet` 的 `blur(20px)` 半屏浮层必须跟着每帧重采样，这笔开销只在播放态出现。

桌面 headless 走 SwiftShader 软件合成，两轮测出的相对开销能从 +67% 漂到 +12%，给不了结论，
所以定量放在真机（MuMu + Via 7.3.3 / Android 15 / WebView 110，视口 360×520、dpr 3）：

| 场景（播放器 + 更多菜单展开） | 平均帧间隔 | P95 | >25ms 长帧率 |
| --- | --- | --- | --- |
| 原样 `blur(20px)` | 22.34ms | 41.66ms | 29.87% |
| 只关掉模糊 | 16.70ms | 16.67ms | 0.21% |

60Hz 下 16.7ms 一帧，>25ms 就是跳过了一帧。结论是**默认开启播放态低特效** `lowFx`。
v0.1.60 真机复验：`glass`（强制把毛玻璃加回来）长帧率 39.33%、平均帧间隔 23.47ms；
`lowfx`（默认）7.16% / 18.14ms，方向正确。

同轮还收掉 `timeupdate` 的几处无意义写入：当前秒文案按秒缓存改 `textContent`、
时长元素引用缓存（直播分支不再每轮 `getElementById('vv-dur')`）、进度条百分比量化到 0.1%
且相同值跳过 inline style 写入（360px 屏上一步 <0.5px，长视频里省掉绝大多数写入）。
这部分是低风险整理，收益远小于模糊层，别把它当成掉帧主因。

工具：`node scripts/perf-playback.mjs`（桌面播放态基准）、`node scripts/mumu-perf-play.mjs`（真机帧率探针）。
桌面那份必须解除 headless 的 60Hz 节流，并垫一层只走 transform 的动态像素逼模糊层重采样，
否则三场景都会被钉成 17ms / 0 掉帧，什么都测不出来。

### 多标签页 / 多播放器（真机实测）

单页反复开关只能证明"关闭时归还"，证明不了"多个页面同时活着时会不会把解码器池占满"。
真机上用 `scripts/android-multitab.mjs` 实测（小米 14 Pro / Android 16 / WebView 143，解码器 `c2.qti.avc.decoder`）：

| 场景 | 峰值存活 | configure / destruct | 结束存活 |
|---|---|---|---|
| 10 个标签页，各播 mp4 直链 | 1 | 10 / 10 | 0 |
| 10 个标签页，各播 m3u8（MSE） | 4 | 10 / 10 | 0 |
| 同一页 10 路 mp4 并发 | 10 | 10 / 10 | 0 |
| 切到子页 → 子页关闭 → 回前台 | 1 | 2 / 1 | 1（前台在播） |

关键结论：

- **mp4 直链后台立刻归还**：`vvEnterBackground` 在同一次调用里 `vvDetachMedia()`（摘 src + load），
  不再等任何定时器。
- **m3u8 走 MSE，同样在进后台那一刻 `stopLoad → detachMedia → destroy` 并摘 src**。
  表里 10 页峰值 4 是旧版"20 秒延迟窗口"留下的数据（3 个后台页 + 1 个前台叠在一起），
  现版本进后台即归还，窗口不存在了。
- **切回被冻结的页签能自动恢复播放**：`vvLeaveBackground → vvResumePlayback`，hls 实例没了就走 `vvRebuildMedia()` 重建，实测画面正常回来。
- 由此修掉一个隐患：`vvReleaseDecoder()` 原来要求 `VV.active.hls` 存在才继续，导致**直链 mp4 在后台永远不主动释放**，只能指望 WebView 冻结时顺手回收。现改为按"有没有在播"判断，直链同样摘 `src` 归还解码器。

测试方法上有两个坑（都写进脚本注释了）：

1. Via 是 singleTask，`am start` 第二次只会把 intent 交给已在最前的实例，**adb 开不出第二个页面**；只能由页面自己 `window.open`。
2. Via 默认拦截弹窗，一次 burst 开 10 个只会成功 1 个；改成**链条式**（每个新页开下一个）才能稳定开到 10 个。另外 `force-stop` 后要等 ~2.8s 再 start，否则 intent 被旧实例吃掉，看到的还是上一次的残留页。

### 开源方案借鉴
Via 不能直接安装 Chrome/Firefox 扩展，但可以借鉴成熟项目的设计，再落到油猴 API 上：

- **cat-catch**（GPL）：借鉴“主清单优先 + 子资源去重”的嗅探思路，以及只保留可播放资源的列表过滤策略；未复制其 GPL 代码。
- **hls.js**（Apache-2.0）：内联 light 构建；参考官方 API 的 `loadPolicy`、`maxBufferHole`、`nudgeOffset`、`nudgeMaxRetry`、`highBufferWatchdogPeriod`、`startFragPrefetch` 等移动端配置，并按 `NETWORK_ERROR` / `MEDIA_ERROR` 分别做 `loadSource`、`startLoad(pos)`、`recoverMediaError`、`swapAudioCodec` 恢复。
- **ArtPlayer / xgplayer**：借鉴画质/音轨菜单的信息层级（清晰度 + 码率、音轨名称 + 语言）和移动端底部 sheet 交互。
- **video.js / Plyr**：借鉴统一的 seek 入口、进度条拖动提交、错误提示和状态恢复方式。

## 安装（Via）

1. 把 `dist/via-video-player.user.js` 发到你手机（网盘/微信/QQ 均可）
   - 若 手机选不中 `.js` 文件，先把后缀改成 `.txt`
2. 打开 Via → 设置 → **通用（或 更多） → 脚本 → 右上角 + → 导入脚本**，选择上述文件
3. 或者：手机上直接打开一个 `.user.js` 结尾的文件链接，网页加载完会弹窗确认安装
4. 进入任意网页点击播放器后，右侧出现蓝紫色圆形角标即为嗅探成功
   - 菜单入口：长按 Via 菜单中的设置，把「脚本」移入菜单一处即可随时开关

> Via 版本 ≥ 4.4.2 支持油猴 API，建议 ≥ 5.x。脚本整体 < 4MB 的限制，本脚本为 ~780KB，安全。

**更新脚本一定要确认版本号变了。** Via 判断「有没有新版」看的是 `@version`，
版本号不动就不会替换代码（历史上一连几轮修复都停在 `0.1.3`，装进手机的其实一直是第一版）。
现在 `build.mjs` 会在产物哈希变化时自动把 patch 位 +1，并把构建时间写进 `@vvbuild`；
装好后打开播放器菜单 →「自检」，第一行会显示 `Via 视频播放诊断 v0.1.x  build YYYY-MM-DD HH:MM`，
和 `dist/` 里的版本对不上就说明还没更新成功。

所以专门用来验证「非当前页是否真的把管线交还了」——这件事桌面 Chromium 测不出来。

环境：MuMu 12（`E:\Program Files\Netease\MuMu`，adb 端口 **16384**，自带的 `nx_main\adb.exe` 才能连）、

测试台：

- `e2e/mumu-tab.html`：模拟"站点自带播放器"的页面，页内 `<video>` 自动播放；
  每 2 秒把 `__vv.front()` 的状态 POST 回服务器。`?d=&max=&alt=` 支持**链条式开标签**
  （Via 是 singleTask，`am start` 开不出第二个标签，只能每页开下一页）。
  - `mode=mp4`：直链（`e2e/media/` 下有 720p / 1080p / H.265 三份对照素材）
  - `mode=hls`：**hls.js + MSE**，每页按标签序号轮换一条**不同的 m3u8**
    （同一个源站的 1080p/720p/480p/380p/240p 五个变体）。这是主流站点的真实形态：
    `blob:` 管线、独立 manifest、独立分片下载、不同码率对应不同解码压力
- `scripts/serve.mjs`：新增 `POST /__report`（把上报追加进 `.tmp/report.log`）与 `/__report/clear`。
- 跨源场景用两个端口（8099 / 8098）轮跳，对应"十个不同视频站"，localStorage 互不可见。

结果（下述每轮都是在 Via 里把脚本更新到当前版本后跑的，自检面板第一行能看到版本号与 build 时间）：

| 场景 | 结果 |
| --- | --- |
| 同源 6 标签（mp4） | 后台 5 个 `bg=true / pipelines=0 / src=0`，前台 1 个 `pipelines=1` 在播 |
| 同源 10 标签（mp4） | 后台 9 个全部 `pipelines=0`，前台 1 个 `pipelines=1`，开窗 9/9 成功 |
| **同源 8 标签（m3u8 / hls.js + MSE，5 种码率轮换）** | 8 个全部 `readyState=4` 起播；后台 7 个在 **29/28/27/26/25/24/23 次采样里 `pipelines` 恒为 0**；前台 1 个恒为 1 |
| **跨源 8 标签（8099/8098 交替 + m3u8）** | 同上，后台 7 个 `pipelines` 恒 0（`localStorage` 互不可见，靠 GM 通道与失焦判定） |
| 切回后台标签 | `visibilitychange` 到达后 1 个心跳内 `bg=false`；mp4 页 `src` 装回并继续播（`why=peer` → `why=bg`）；**MSE 页不装回已关闭的 blob**（`pipelines=0`，不留假管线），弹「点「重载」恢复播放」 |
| **切走再切回（内置播放器放 m3u8，0.1.16）** | 切走：`pipelines` 1→0、播放器 `muted=true / vol=0`（主动交还）；切回：`bg=false` 后 **`muted=false / vol=1`**、`pipelines` 回到 1、画面继续播 |
| **切走再切回（站点原生播放器）** | 切走 `muted=true`（拆解）；切回 `muteBy=restore`、`muted=false`、`restoreCount+1`，改动**在 1 个心跳内**完成 |
| 杀进程后重开 | 恢复的标签**懒加载**，没有上报、不建 WebView，因此不占解码器 |

结论：**释放链路在真实 Via 里是通的**（同源/跨源、mp4/m3u8、6/8/10 页都成立），
剩下能解释真机失败的只有两类：① 真机跑的是旧脚本（Via 会按路径缓存 + 注入已装脚本）；
② 设备硬件解码器配额确实被物理占满（模拟器只有 `c2.android.*` 软件解码器，这一条**测不出来**）。

#### 这套自动化里踩到的四个坑（都会让结论完全失真）

1. **`adb shell` 会把 `&` 当成命令分隔符**。写成
   `am start -d "http://…?id=A&max=8&mode=hls"` 时，设备端 shell 只收到 `?id=A`，
   后面的参数全被当成后台命令丢掉——页面照常打开、视频照常播，但 `mode` 退回默认、
   `vvdebug` 没开，看起来就像「脚本没注入」。正确写法是把整条命令和 URL 分别包一层单引号：
   `adb shell "am start -n mark.via/.Shell -a android.intent.action.VIEW -d 'http://…?a=1&b=2'"`
2. **Via 的页面缓存按路径命中**，`Cache-Control: no-store` 和 `?t=时间戳` 都拦不住
   （子资源同理，所以脚本走 `/dist/vv-<数字>.js`）。改了测试页却还在跑旧版，
   诊断字段对不上会白测一轮。服务端加了 `mumu-tab-<任意>.html → mumu-tab.html` 的别名映射，
   每轮换一个 `-rN` 路径就能强制换 key。
3. **`pm clear mark.via` 会连用户脚本一起删掉**，而且删完还得重新走一遍
   「设置 → 脚本 → ＋ → 下载脚本 → 输地址 → 确认更新」。更隐蔽的是：脚本 `@version`
   一直写死 `0.1.3` 时，Via 判定「没有新版」，点了更新也不会换代码——
   这正是「改了几轮还是没作用」的一个真实来源。现在 `build.mjs` 按产物哈希自动递增 patch 位，
   并把 build 时间写进头部，自检面板第一行直接显示 `vX.Y.Z build …`，装的是哪版一眼可辨。
4. **每次 `am start … -d URL` 都会新开一个标签页，而被压到后台的标签会被 Chromium 冻结**：
   `setInterval` 不再触发、`fetch` 不再发出、DOM 改动也不再重绘。表现为「视频永远 `rs=0`、
   页面计数器停在 1」，非常像「脚本把视频搞坏了」。判据：底部工具栏的标签数必须是 **1**，
   或者看页面上报里 `hidden` 是否为 false。改测内容时优先用「改写同一个文件 + 点地址栏的刷新」，
   而不是反复 `am start`。

> 模拟器的局限必须说清楚：x86_64 镜像只有 AOSP 软件解码器，实例数几乎不受限，
> 所以「十个页签里只有前台能播」这个**症状不会复现**，它只能证明"我们是否交还"，
> 不能证明"设备配额够不够"。判断后者仍要看真机 `dumpsys media.metrics` 的 cfg/des 计数。

### 多站点分发策略实测（`node scripts/site-matrix.mjs`）

不同站点的分发方式差别很大，逐个跑一遍看覆盖面和缺口（下表以代号表示，只保留分发策略层面的差异）。脚本要实测的站点清单不随仓库分发：把 `e2e/sites.example.json` 复制成 `e2e/sites.local.json`，填好自己的目标地址即可（该文件已在 `.gitignore` 中）。

| 站点 | 分发策略 | 嗅探 | 内置播放 | 说明 |
| --- | --- | --- | --- | --- |
| 站点 1 | 多码率 HLS + 多 CDN 冗余 + `blob:`（MSE） | 5 条（含音轨清单） | ✅ `rs=4` | 画质 4 档可切；进度用缓冲时长算 |
| 站点 2 | 直链 `mp4`（对象存储 CDN） | 4 条 | ✅ `rs=4` | 字节进度可用，起播最快 |
| 站点 3 | `mp4` + `vkey` 时效直链、加密 HLS、`blob:` | 8 条 | ✅ `rs=4` | `vkey` 有时效但窗口内可复用 |
| 站点 4 | HLS + **一次性 `pm` token** + 三 CDN 冗余 | 5 条 | ❌ `rs=0` | 页面播放器先消费了 token，第三方再请求必 403 |
| 站点 5 | **仅 `blob:`**（MSE 会话句柄） | 1 条 | ❌ `rs=0` | 离开页面上下文拿不到数据 |

结论：**直链 / HLS 类（3/5）能直接接管播放；一次性鉴权与纯 `blob:` 类（2/5）在原理上就做不到**。
对这 2 类站点，现在的行为不再是"黑屏 + 无限转圈"，而是弹出**起播失败卡片**：

- 标题「这个视频源播不了」+ 具体原因（`HTTP 403 拒绝第三方播放` / `这是页面自己 MSE 会话的句柄（blob）` / `起播超时`）
- 三个出口按钮：**重试** / **外部播放器** / **返回**
- 触发条件：HLS 拿到 401/403 立即弹（不再无意义重试）；直链 `MEDIA_ERR_SRC_NOT_SUPPORTED` 或 `blob:` 立即弹；其余情况 12s 看门狗兜底


> 抗遮挡测试方法：向 `<html>` 末尾注入 `position:fixed; z-index:2147483647` 的全屏假广告，插件界面会在一轮检测内重新置顶。
>
> 实测环境到 Apple test streams 的 hls.js XHR 受 CORS/代理限制（原生 `<video>` 能播，但 hls.js 拉不到清单），属环境问题；HLS 播放/seek 用 CORS 可用的 unified-streaming 与 bitdash 验证。Via 真机上以实际站点为准。

## 已知限制（同油猴生态的共性）

| 限制 | 说明 |
| --- | --- |
| blob 原生流 | 部分站点的加密流（MSE 会话内的 `blob:`）不可导出下载，只能页内播放 |
| m3u8 下载 | Via 无 m3u8 转 mp4 能力，请用导出的 `.m3u` 或 `curl` 交给 N_m3u8DL-RE / ffmpeg |
| 防盗链 | 页内播放自带页面上下文，不受影响；复制裸链给外部播放器多半会被拒，需用「导出 .m3u」带上 Referer |
| 一次性签名 | 部分站点的 token 只能用一次或几分钟内失效，导出后立刻用，过期只能回页面重新嗅探 |
| mp4 跳转 | 服务器需支持 HTTP Range；不支持时播放器会提示“该视频不支持跳转”，只能从头播放或下载 |
| iframe | Via 不支持给 iframe 注入脚本，跨域 iframe 里的视频嗅不到 |
| 亮度 | WebView 无系统级亮度权限，用黑色遮罩模拟 |
| 音量 | iOS WebView 不监听 JS 音量调整（受系统静音开关影响）；安卓 WebView 一般可用 |
| 浏览器顶层弹层 | 使用 `dialog.showModal()` / popover top layer 的广告不受 z-index 控制，本方案无法压过；普通 fixed/absolute 广告可以覆盖 |
| 卡顿归因 | 诊断里的「负载 = 播放消耗 ÷ 下载速率」。≥100% 是源/CDN 限速，换播放策略没用；<60% 仍卡才查软解与策略 |
| 解码器耗尽 | Android WebView 的 MediaCodec 实例数是硬上限，多开 m3u8 页面会耗尽；**关掉其他标签页**（不是切后台）就能归还解码器，不必重启 Via。脚本已把并发收敛到 1、在挂起时释放解码器、并在后台自动休眠回收资源，但无法突破系统上限 |

每次改动都要在 `CHANGELOG.md` 的「未发布」段写清「改了什么、为什么改」（只改文档、注释、测试也算），
然后跑 `node build.mjs`：它会按产物哈希自增 `@version`，并把「未发布」段自动定版为
`## v新版本 — 日期`、补一个空的「未发布」段。**不必一个版本号一条**——跨了几个版本会合并成
`## v0.1.53–v0.1.55 — 日期` 这样的区间，中间过渡版本不用单独记。漏记时构建会打印
`!!! CHANGELOG 漏记 !!!`，而且每次构建都提醒，直到补上为止（只提醒不阻断，中间构建不会被卡住）。

真机（需 adb 连接、Via 已放开弹窗拦截）：

```
node scripts/android-multitab.mjs --pages=10 --mode=hls --spawn=8000
node scripts/android-multitab.mjs --pages=10 --mode=mp4
node scripts/android-multitab.mjs --recover      # 后台释放 + 回前台恢复
node scripts/android-close-tab.mjs --mode=mp4     # 直接关标签页时是否释放
node scripts/android-close-tab.mjs --mode=hls     # 同上，走 MSE 路径
```

`e2e-verify.mjs` 会自动起本地服务器、驱动无头 Chrome 走完整链路，并在 URL 带 `?vvdebug=1` 时
用到 `window.__vv` 调试句柄（`VV` / `hlsConfig` / `hlsSeekMode` / `diag`），不影响普通用户。
