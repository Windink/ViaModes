# mumu-measure · 真机定量测量

## 用途

回答「这个改动到底有没有让用户感知到更快」。真机测量最容易出的不是设备问题，而是**方法问题**：
量错冷热、没存基线、事后挑阈值、用平均值掩盖长尾——每一个都能得出反向结论。

## 何时用

- 性能、起播耗时、帧率、每页执行成本这类改动，要在动手前判断「值不值得做」
- 改完了要证明「确实变好了」，而不是「感觉快了」
- 要复现历史结论（某个优化为什么当时决定不做）

## 输入

- 待测指标（耗时 / 帧间隔 / 长帧率 / 字节速率）
- 基线：同一设备、同一素材、同一参数下的一份旧数据
- 候选：改动后的构建

## 输出

- 中位数对比（必要时加 P95 / 长帧率）
- 一句结论：越过门槛 / 没越过 / 样本不足无法判断
- 可复跑的命令与参数（写进 README 对应章节）

## 依赖

- `mumu-device`（连接、自检）
- `mumu-deploy`（版本对齐；基线版本与候选版本都要能准确识别）
- 对应测量脚本：`mumu-resume`（`SAVE=1`）、`mumu-perf-play`、`mumu-hlsperf`、`mumu-open-ab`

## 六条原则

### 1. 门槛先写死进脚本，再开始量

阈值必须在看数据之前确定，并且写进脚本注释/常量里。否则一定会变成「量完挑一个顺眼的阈值」。

```js
// 真机 60Hz 下一帧 16.7ms；省不到 2 帧（33ms）用户感知不到，那就不值得为它多一条会坏的加载路径
const FRAME_MS = 16.7;
const NOISE_MS = FRAME_MS * 2;
```

### 2. 必须先存基线

```bash
SAVE=1 node scripts/mumu-resume.mjs      # 存成 .tmp/resume-baseline.json
node scripts/mumu-resume.mjs             # 改完之后跑，自动打印对比
```

没有基线时，任何「优化后 240ms」都无法判断是好是坏。

### 3. 冷轮才是成本，热轮是缓存

「每开一个页面付一次的钱」只能按冷轮算：新页面 = 新 realm，脚本要重新解析编译。
同一个页面里跑第二次是热态，数字会小一个量级——拿热态当成本会得出「成本可忽略」的错误结论。

同理，计时之前要**静置**：刚跑完一轮时主线程还有余温，冷轮会漂。

### 4. 交替配对，别「先跑完 A 再跑完 B」

网络、站点侧、设备温度都会随时间漂。正确做法是 A→B→A→B 交替 N 对，取每对差值的分布，
抖动就被摊到两臂上了。`mumu-real-ab` 就是这么做的（`PAIRS=3`）。

### 5. 中位数 + 分布，不是平均值

平均值被长尾吃掉。帧率类指标必须同时看 P95 与长帧率（>25ms 的帧占比），
耗时类看中位与 P95。真机基线示例：半屏 `blur(20px)` 平均 22.34ms / P95 41.66ms / 长帧率 29.87%——
平均只高 34%，但三分之一的帧是长帧，用户感知到的是「卡」而不是「慢一点」。

### 6. 一次只改一个变量

同时改「去掉毛玻璃」和「减少 DOM 写入」，量出来的收益无法归因，也就无法决定留下哪一半。
需要一次改多处时，先分别量，再合起来验一次。

## 桌面测什么、不测什么

| 适合桌面（快、便宜、可批量） | 必须真机 |
| --- | --- |
| 逻辑正确性、状态机、配置对象取值 | 帧率与掉帧（headless 被钉在 60Hz，量不出 `backdrop-filter` 的真实开销） |
| DOM 结构、CSS 计算值 | 起播耗时（没有真实 MediaCodec） |
| 慢网判据的时间线（用 `slow-serve` 模拟） | 系统画中画、WebView 特有能力差异 |
| 每页脚本解析成本的量级（Node vm） | 一切「用户能不能看见」的问题 |

`perf-playback.mjs` 这类桌面基准必须加 `--disable-frame-rate-limit --disable-gpu-vsync`，
还要垫一层只走 transform 的动态像素逼模糊层重采样，否则测的是一张静态图。
即使这样，**定量结论仍以真机探针为准**。

## 写结论时的口径

- 写清设备与版本：`MuMu / Via 7.3.3 / WebView 110`
- 写清样本数：`N 轮中位数`、`N 对交替`
- 写清单位与判定：`22.34ms → 16.70ms，越过 25ms 跳帧线`
- 不写「快了很多」「明显改善」——不可复查的形容词等于没结论
